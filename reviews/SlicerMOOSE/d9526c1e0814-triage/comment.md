Suggestions for a later update:

- [`MOOSE/MOOSE.py:275-276`](https://github.com/mprires/SlicerMOOSE/blob/d9526c1e0814bad1eb49349a73684544f690d078/MOOSE/MOOSE.py#L275-L276): If PythonSlicer is not on PATH (e.g. unusual launch environment), self.python_slicer is None and launchConsoleProcess receives None as argv[0], failing with an obscure error instead of a clear message. Similarly the moosez console script path is assumed rather than checked for existence. Fall back to slicer.util.launchConsoleProcess with sys.executable or raise a clear InstallError when PythonSlicer/moosez are not found.
- [`MOOSE/MOOSE.py:381`](https://github.com/mprires/SlicerMOOSE/blob/d9526c1e0814bad1eb49349a73684544f690d078/MOOSE/MOOSE.py#L381): On a non-zero return code, the code raises CalledProcessError with output=proc.stdout, which is the stream object, not captured output, and stderr=proc.stderr is not set by launchConsoleProcess. The user sees a confusing message rather than the moosez error text, which makes failures harder to diagnose. Pass the collected output (returnOutput=True) and report it to the user.
- [`MOOSE/MOOSE.py:312-313`](https://github.com/mprires/SlicerMOOSE/blob/d9526c1e0814bad1eb49349a73684544f690d078/MOOSE/MOOSE.py#L312-L313): The readline loop in forward_process_status calls slicer.app.processEvents() via the status callback, so the UI is not fully frozen, but the whole run (up to ~40 minutes on CPU per README) executes inside the button slot with no progress bar, no cancel button and no way to abort; the module widget is disabled for the duration. Run the subprocess in a worker thread (e.g. slicer.util.Process or a QThread) with a progress dialog and a cancel action.
- [`MOOSE/MOOSE.py:192-195`](https://github.com/mprires/SlicerMOOSE/blob/d9526c1e0814bad1eb49349a73684544f690d078/MOOSE/MOOSE.py#L192-L195): If the moosez JSON's organ_indices does not contain every label index present in the NIfTI (or the segment ID is not of the form Segment_<int>), the loop raises KeyError/ValueError after the segmentation node has already been added to the scene, so the user sees 'Segmentation failed.' even though a segmentation exists, and the temp folder is not cleaned up. Use label_indices.get(segmentID_numeric) and skip/keep the default name when missing; guard the int() conversion.
- [`MOOSE/MOOSE.py:197`](https://github.com/mprires/SlicerMOOSE/blob/d9526c1e0814bad1eb49349a73684544f690d078/MOOSE/MOOSE.py#L197): moose_folder is created with slicer.util.tempDirectory() and only removed on the success path at line 197. Any exception (missing segmentation, KeyError while renaming segments, subprocess failure) leaves the copied CT volume and moosez outputs on disk; repeated failures accumulate patient image copies in the temp directory. Move the cleanup into a finally block (or use a try/finally around prepare_data/run_segmentation).
- [`MOOSE/MOOSE.py:445-459`](https://github.com/mprires/SlicerMOOSE/blob/d9526c1e0814bad1eb49349a73684544f690d078/MOOSE/MOOSE.py#L445-L459): The integration test writes sample_CT.nii.gz into the user's ~/Downloads (or %USERPROFILE%\Downloads) and later calls os.remove(sampleVolume_path) (line 439). If a user already has a file with that name there, it is silently overwritten and then deleted. The download is also not integrity-checked. Download into slicer.util.tempDirectory() (or a TemporaryDirectory) instead of the user's Downloads folder, and delete only that temporary copy.
