Suggestions for a later update:

- [`ImpactSynth/ImpactSynth.py:17-22`](https://github.com/vboussot/SlicerImpactSynth/blob/188d1959ef0c6782fcebc9a533b0ccb9964410bf/ImpactSynth/ImpactSynth.py#L17-L22): Slicer imports scripted-module Python files when it scans the extension module paths at startup, so this top-level import executes for every user of that Slicer installation, including users who never open Impact Synth. Whatever KonfAI pulls in at import time (its widgets, and potentially torch/other heavy dependencies) then affects startup time and memory for everyone. The same file re-imports KonfAI inside setup() (line 100), which suggests the author was aware heavy imports belong in setup() but the top-level import was left in place. Move the KonfAI imports into ImpactSynthWidget.setup() (and store the classes on the instance) or into a try/except that reports a clear message, so that importing the module file has no third-party side effects.
- [`ImpactSynth/ImpactSynth.py:18`](https://github.com/vboussot/SlicerImpactSynth/blob/188d1959ef0c6782fcebc9a533b0ccb9964410bf/ImpactSynth/ImpactSynth.py#L18): The module depends on an underscore-prefixed private symbol of KonfAI in a top-level import. A refactor of KonfAI's internals produces an ImportError while Slicer imports this file, so the module disappears from the module selector with only a console traceback instead of a readable diagnostic, even though the public API version check at lines 102-109 would otherwise have handled incompatibilities gracefully. Import `_is_reload_setup` defensively (e.g. getattr on the KonfAI module inside setup(), defaulting to a no-op or reporting the incompatibility through the existing API-version message).
- [`ImpactSynth/Testing/Python/CMakeLists.txt:2`](https://github.com/vboussot/SlicerImpactSynth/blob/188d1959ef0c6782fcebc9a533b0ccb9964410bf/ImpactSynth/Testing/Python/CMakeLists.txt#L2): ImpactSynth/CMakeLists.txt:26 registers `slicer_add_python_unittest(SCRIPT ImpactSynth.py)`, but ImpactSynth.py contains no test class, and the dedicated test CMake entry is commented out. Consequently nothing exercises the widget construction, the KonfAI API-version guard, or the app registration in CI, so a broken dependency or a wrong app identifier would only be discovered by a user opening the module. Add a minimal module test (instantiate the widget / check the app identifiers resolve) and enable it in ImpactSynth/Testing/Python/CMakeLists.txt.
- [`ImpactSynth/ImpactSynth.py:85`](https://github.com/vboussot/SlicerImpactSynth/blob/188d1959ef0c6782fcebc9a533b0ccb9964410bf/ImpactSynth/ImpactSynth.py#L85): Without `from __future__ import annotations` this annotation is evaluated when the class body is executed, i.e. while Slicer imports the module file; on a Slicer built with Python 3.9 this raises TypeError and the module never loads. The README requires Slicer >= 5.10, so the practical risk depends on which Python that Slicer bundles - I could not verify it here. The pre-commit config (`--py310-plus`) confirms 3.10 is the intended minimum. Either add `from __future__ import annotations` or use `typing.Optional[QWidget]` to keep the module importable on older Python builds, and state the minimum Slicer/Python version in the README.
- [`CMakeLists.txt:13`](https://github.com/vboussot/SlicerImpactSynth/blob/188d1959ef0c6782fcebc9a533b0ccb9964410bf/CMakeLists.txt#L13): README.md:133 instructs users to install the PyTorch extension manually and KonfAI inference needs torch, but neither the catalog entry ('build_dependencies': ['KonfAI']) nor EXTENSION_DEPENDS mentions PyTorch. A user who installs only ImpactSynth and misses step 1 gets an inference failure instead of having the dependency pulled in by the Extensions Manager (unless the separate KonfAI entry already declares PyTorch). Add PyTorch (and keep it consistent with the catalog entry's build_dependencies) if the KonfAI entry does not already declare it, or document explicitly that PyTorch is an indirect dependency satisfied by KonfAI.
