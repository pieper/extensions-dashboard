Please fix these before the extension can be merged:

- [`BigImageViewer/BigImageViewer.py:17-21`](https://github.com/gaoyi/SlicerBigImage/blob/15af77d3d348e9a3dce63131ca1a1ce9ddfcaea6/BigImageViewer/BigImageViewer.py#L17-L21): `BigImageViewer.py` calls `slicer.util.pip_install("tiffslide")` at module import time. Slicer imports all scripted loadable modules during application startup to discover and register them, so installing this extension causes `pip install tiffslide` (and its dependency tree, including `tifffile`, `imagecodecs`, and `zarr`) to run unconditionally on Slicer startup without user confirmation, even for users who never open the BigImageViewer module. This also contradicts `README.md` line 29, which states packages are installed on first use. Move the `tiffslide` import and `pip_install("tiffslide")` out of the module top level and into `BigImageViewerLogic.installPreRequisites()` (or a lazy helper called when the user actually loads a slide), with user confirmation or a status message before installing.

Smaller suggestions:

- [`BigImageViewer/BigImageViewer.py:165-173`](https://github.com/gaoyi/SlicerBigImage/blob/15af77d3d348e9a3dce63131ca1a1ce9ddfcaea6/BigImageViewer/BigImageViewer.py#L165-L173): In `BigImageViewerWidget.__init__`, five VTK observers are added directly to the Red slice view interactor via `interactor.AddObserver(...)` instead of `self.addObserver(...)`, and their observer tags are never stored or removed on `exit()` or `cleanup()`. Additionally, `__init__` immediately forces `lm.setLayout(6)` (Red slice only). Once the user opens `BigImageViewer` once, scrolling the mouse wheel or left-clicking and releasing in the Red slice view continues to trigger `BigImageViewer` callbacks (`onLeftButtonReleased`, `onMouseWheelForwardEvent`, etc.) even after switching to other Slicer modules. Use `self.addObserver(...)` (from `VTKObservationMixin`) or store and remove the observer tags when leaving the module (`exit()`) and in `cleanup()`, and only change layout or attach Red view interactor observers when the module is active (`enter()`).
- [`NgffImageIO/NgffImageIO.py:53-62`](https://github.com/gaoyi/SlicerBigImage/blob/15af77d3d348e9a3dce63131ca1a1ce9ddfcaea6/NgffImageIO/NgffImageIO.py#L53-L62): Volume conversion and Zarr writing call this helper and can install zarr, dask, and xarray into the shared environment without asking; the viewer similarly installs scikit-image when loading a slide. Pip may also change shared dependencies, affecting other modules. Offer a user-confirmed dependency setup with compatible requirements and a clear cancellation path, rather than silently invoking pip during conversion or loading.
- [`NgffImageIO/NgffImageIO.py:209-212`](https://github.com/gaoyi/SlicerBigImage/blob/15af77d3d348e9a3dce63131ca1a1ce9ddfcaea6/NgffImageIO/NgffImageIO.py#L209-L212): `NgffImageIOFileReader.load()` imports `xarray` and `zarr` directly without calling `NgffImageIOLogic.installRequiredPythonPackages()` first (whereas `NgffImageIOFileWriter.write()` calls `xarrayFromVolume()`, which calls `installRequiredPythonPackages()`). If a user loads a `.zarr` file via Slicer's standard Add Data dialog before ever exporting one, `import xarray` or `import zarr` will raise `ModuleNotFoundError` and the file load will fail. Call `NgffImageIOLogic.installRequiredPythonPackages()` at the beginning of `NgffImageIOFileReader.load()` before importing `xarray` and `zarr`.
- [`BigImageViewer/BigImageViewer.py:1214`](https://github.com/gaoyi/SlicerBigImage/blob/15af77d3d348e9a3dce63131ca1a1ce9ddfcaea6/BigImageViewer/BigImageViewer.py#L1214): Calling `installPreRequisites()` (which happens whenever a WSI is loaded) mutates the process-wide environment variable `CUDA_VISIBLE_DEVICES` to `"0"`, affecting any other Slicer modules or extensions running in the same Slicer process. Moreover, `BigImageViewer` does not actually use CUDA in its active code. Remove `os.environ["CUDA_VISIBLE_DEVICES"] = "0"` from `installPreRequisites()`.
- [`NgffImageIO/NgffImageIO.py:115-118`](https://github.com/gaoyi/SlicerBigImage/blob/15af77d3d348e9a3dce63131ca1a1ce9ddfcaea6/NgffImageIO/NgffImageIO.py#L115-L118): In `NgffImageIOLogic.xarrayFromVolume()`, the loop variable is `attributeName`, but the dictionary assignment uses an undefined variable `key` (`attrs[key] = ...`). Whenever a `volumeNode` has any MRML attributes (`volumeNode.GetAttributeNames()` is non-empty), `xarrayFromVolume` (and thus `NgffImageIOFileWriter.write`) will fail with `NameError: name 'key' is not defined`. Replace `attrs[key] = volumeNode.GetAttribute(attributeName)` with `attrs[attributeName] = volumeNode.GetAttribute(attributeName)`.
- [`BigImageViewer/BigImageViewer.py:57`](https://github.com/gaoyi/SlicerBigImage/blob/15af77d3d348e9a3dce63131ca1a1ce9ddfcaea6/BigImageViewer/BigImageViewer.py#L57): In `BigImageViewerTest.test_BigImageViewer1`, `registerSampleData()` is commented out, so `'BigImageViewer1'` is never registered with `SampleData`. Running the self-test will fail when trying to download `'BigImageViewer1'`, and `BigImageViewerLogic.process()` only runs the template `thresholdscalarvolume` CLI rather than testing any `BigImageViewer` functionality. Furthermore, the C++ tests in `ColorDecomposition/Testing/Cxx/CMakeLists.txt` and `NucleusSegmentation/Testing/Cxx/CMakeLists.txt` pass `--sigma 2.5` (from the template CLI) which neither CLI accepts. Update the Python and C++ tests to pass valid arguments and sample data for the actual modules.
- [`NucleusSegmentation/include/utilitiesIO.hxx:34-39`](https://github.com/gaoyi/SlicerBigImage/blob/15af77d3d348e9a3dce63131ca1a1ce9ddfcaea6/NucleusSegmentation/include/utilitiesIO.hxx#L34-L39): `NucleusSegmentation` is built via `SEMMacroBuildCLI` (which builds both a shared-library CLI module and an executable). Throughout `NucleusSegmentation` (`utilitiesIO.hxx`, `SFLSSegmentor2D.hxx`, `BinaryMaskAnalysisFilter.cxx`, `HAndEImageAnalysisFilter.cxx`, `HematoxylinImageSegmentationFilter.cxx`) and `ColorDecomposition.cxx` (line 69), error handling calls `raise(SIGABRT)` or `abort()`. If the CLI is executed in-process as a shared library (or if an invalid/corrupt image or parameter is encountered), calling `abort()` / `raise(SIGABRT)` terminates the entire Slicer application instead of returning `EXIT_FAILURE`. Throw an exception (`itkGenericExceptionMacro` or `std::runtime_error`) and catch it in `main()` (the CLI entry point) to return `EXIT_FAILURE` cleanly instead of calling `abort()` or `raise(SIGABRT)`.
