Suggestions for a later update:

- [`Label/Logic/vtkSlicerLabelLogic.cxx:145-148`](https://github.com/chir-set/SlicerExtraMarkups/blob/f5c833befbd67d8e58f0103c1efffa594c66dc93/Label/Logic/vtkSlicerLabelLogic.cxx#L145-L148): GetMRMLScene() can return nullptr (the same function checks it in RegisterNodes and OnMRMLSceneNodeAdded), but here it is dereferenced unconditionally, so a call during scene teardown would crash. In addition, `colorTable->GetColor(this->NextColorIndex, rgba)` is called before the wrap-around check, so when NextColorIndex equals GetNumberOfColors() the lookup fails and the previous rgba value is reused. The identical code is duplicated in Shape/Logic/vtkSlicerShapeLogic.cxx:135-156. Guard against a null scene and clamp/wrap NextColorIndex before calling GetColor; consider sharing one implementation between the two logic classes.
- [`Label/VTKWidgets/vtkSlicerLabelWidget.h:21-22`](https://github.com/chir-set/SlicerExtraMarkups/blob/f5c833befbd67d8e58f0103c1efffa594c66dc93/Label/VTKWidgets/vtkSlicerLabelWidget.h#L21-L22): Shape/VTKWidgets/vtkSlicerShapeWidget.h:21-22 uses the identical guard `__vtkslicerslicingcontourwidget_h_`. Any translation unit that includes both headers (for example a future module or test that uses both widgets) silently loses the second class declaration and fails to compile with confusing errors. The same copy-paste also produced `void operator=(const vtkSlicerLabelWidget) = delete;` (line 49) with a by-value parameter instead of a reference. Give each header a unique guard (e.g. __vtkSlicerLabelWidget_h_ / __vtkSlicerShapeWidget_h_) and fix the deleted assignment operator signature.
- [`Label/qSlicerLabelModule.cxx:107-110`](https://github.com/chir-set/SlicerExtraMarkups/blob/f5c833befbd67d8e58f0103c1efffa594c66dc93/Label/qSlicerLabelModule.cxx#L107-L110): Both modules report the 'Testing.TestCases' category (Shape/qSlicerShapeModule.cxx:107-110) and are hidden (isHidden() returns true), so users only find them through the Markups module's options widget. The repository contains no test directory and no sample scene, and the READMEs give no statement about suitability for clinical measurement, even though the Shape node computes lengths, areas and volumes that a user might read as measurements. Add a short disclaimer about measurement accuracy/clinical use, provide a sample scene or test data, and consider a more descriptive category than Testing.TestCases.
- [`Shape/MRML/vtkMRMLMarkupsShapeNode.cxx:45`](https://github.com/chir-set/SlicerExtraMarkups/blob/f5c833befbd67d8e58f0103c1efffa594c66dc93/Shape/MRML/vtkMRMLMarkupsShapeNode.cxx#L45): GetShapeNameFromString returns -1 for an unknown string (lines 151-168), and the JSON storage node passes that straight to SetShapeName (Shape/MRML/vtkMRMLMarkupsShapeJsonStorageNode.cxx:90). SetShapeName assigns ShapeName = -1 first and then hits `default : vtkErrorMacro("Unknown shape."); return;` (lines 325-327), so the node ends up with ShapeName == -1 while RequiredNumberOfControlPoints/MaximumNumberOfControlPoints and the measurements still describe the previous shape. GetShapeNameAsString(-1) then returns an empty string, which is written back on the next save. Validate the incoming value before assigning (reject negative values), and have the storage node ignore an unknown shape name instead of applying it.
- [`Label/Logic/vtkSlicerLabelLogic.cxx:133`](https://github.com/chir-set/SlicerExtraMarkups/blob/f5c833befbd67d8e58f0103c1efffa594c66dc93/Label/Logic/vtkSlicerLabelLogic.cxx#L133): The array 'colour' is read in its own initializer before it is assigned, so the values are indeterminate. The same line exists in Shape/Logic/vtkSlicerShapeLogic.cxx:126. The result is an unpredictable unselected-colour on markups created with alternate colours. This is not a security issue. The intended value is probably 1.0 minus the selected colour components. Compute the unselected colour from selectedColour, e.g. double colour[3] = { 1.0 - selectedColour[0], 1.0 - selectedColour[1], 1.0 - selectedColour[2]}; in both files.
