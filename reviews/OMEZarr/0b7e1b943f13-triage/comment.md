Suggestions for a later update:

- [`OMEZarr/OMEZarr.py:386-394`](https://github.com/fideus-labs/SlicerOMEZarr/blob/0b7e1b943f13d78504ed58f17f5e4ba4c9f9c48d/OMEZarr/OMEZarr.py#L386-L394): The dependency is installed into Slicer's shared Python environment the first time any OME-Zarr store is opened (including via slicer.util.loadNodeFromFile or drag-and-drop). When there is no main window or testing is enabled, `interactive` is false and pip_install runs with no confirmation at all, so a scripted or headless session modifies the shared environment without asking. In the GUI the confirmation is present, which is the acceptable path; the non-interactive path is the gap. Refuse to install (and raise a clear error telling the user to install ngff-zarr) when no interactive confirmation is possible, or gate the silent install behind an explicit opt-in setting.
- [`OMEZarr/OMEZarr.py:380`](https://github.com/fideus-labs/SlicerOMEZarr/blob/0b7e1b943f13d78504ed58f17f5e4ba4c9f9c48d/OMEZarr/OMEZarr.py#L380): Every opened store (and every scene image, line 1053) is kept in a process-wide dict of lazy dask-backed multiscales for the lifetime of the Slicer session; clearCache() exists but I found no call to it in the code I read. Opening many large stores in one session accumulates metadata and open store handles. Bound the cache (e.g. keep the last few stores) or clear it on scene close.
- [`OMEZarr/OMEZarr.py:284-291`](https://github.com/fideus-labs/SlicerOMEZarr/blob/0b7e1b943f13d78504ed58f17f5e4ba4c9f9c48d/OMEZarr/OMEZarr.py#L284-L291): runResponsive keeps the UI responsive by calling processEvents in a loop, which lets the user trigger other actions (closing the scene, deleting nodes, starting another load) while a volume is being written into a preallocated VTK buffer. This is a pragmatic pattern rather than a defect, but re-entrancy during a load is not guarded. Disable the module panel and the load actions while a load is in progress, or document the re-entrancy assumption.
