Suggestions for a later update:

- [`NeuroStrip/NeuroStrip.py:411-413`](https://github.com/dyollb/SlicerNeuroStrip/blob/1576f50b2883dede76ac284782caf166b6b3760c/NeuroStrip/NeuroStrip.py#L411-L413): The test asserts an exact maximum intensity of 605, which depends on the model version and preprocessing; any model update or minor numerical difference will fail the test even when the module works. It also requires the pip dependency to be installed, so the test cannot run in a clean build environment. Assert structural properties (non-empty mask, mask values in {0,1}, masked volume zero outside the mask) instead of exact intensity values.
- [`NeuroStrip/NeuroStrip.py:263-271`](https://github.com/dyollb/SlicerNeuroStrip/blob/1576f50b2883dede76ac284782caf166b6b3760c/NeuroStrip/NeuroStrip.py#L263-L271): The whole prediction (potentially minutes on CPU) runs inside the button handler with only a wait cursor; Slicer's UI is frozen and the user gets no progress or cancel option, which looks like a hang for large volumes. Errors are at least surfaced via tryWithErrorDisplay, so this is a usability/robustness issue rather than a safety one. Run the prediction in a background thread/CLI node with progress reporting, or at minimum show a modal progress dialog and process events.
- [`NeuroStrip/NeuroStrip.py:323-328`](https://github.com/dyollb/SlicerNeuroStrip/blob/1576f50b2883dede76ac284782caf166b6b3760c/NeuroStrip/NeuroStrip.py#L323-L328): process() calls neurostrip.predict in the main thread, so the Slicer UI freezes for the whole CNN run on a full MRI volume. The README acknowledges that processing takes time. A user may think Slicer has hung, and the window may be marked unresponsive. Show a progress dialog or run inference in a worker thread, with an explicit device choice (the CPU is hardcoded at line 327).
- [`NeuroStrip/NeuroStrip.py:182-186`](https://github.com/dyollb/SlicerNeuroStrip/blob/1576f50b2883dede76ac284782caf166b6b3760c/NeuroStrip/NeuroStrip.py#L182-L186): If the user cancels the installation dialog, `_dependenciesInstalled` stays False and the confirmation dialog reappears every time the module is entered; conversely, after a successful install the flag is not re-checked, so a failed install is only detected on the next Apply. Minor UX issue. Remember the user's decline for the session and re-check availability before running the algorithm.
