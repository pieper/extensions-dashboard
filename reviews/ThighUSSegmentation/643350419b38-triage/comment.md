Suggestions for a later update:

- [`ThighUSSegmentation/ThighUSSegmentation.py:496-500`](https://github.com/UPNa-Biomedical-Engineering-Group/SlicerThighUSSegmentation/blob/643350419b387f40c98699944d03c23e9cfd2b02/ThighUSSegmentation/ThighUSSegmentation.py#L496-L500): Every Apply prepends Slicer's Python script directories to the global `PATH`, which affects subprocesses launched by any other module or extension for the rest of the session. It is not restored on completion or module close. Pass the resolved executable path directly to the pipeline (or set PATH only for the duration of the call and restore it afterwards).
- [`ThighUSSegmentation/CMakeLists.txt:9-11`](https://github.com/UPNa-Biomedical-Engineering-Group/SlicerThighUSSegmentation/blob/643350419b387f40c98699944d03c23e9cfd2b02/ThighUSSegmentation/CMakeLists.txt#L9-L11): `ThighUSSegmentation.png` (1,756,998 bytes) exists both at the repository root (used only as the catalog icon URL) and at `ThighUSSegmentation/Resources/Icons/ThighUSSegmentation.png` with the identical size, so roughly 3.5 MB of binary is committed for one icon. This is not a load failure, but a module icon of that size is unnecessary. Downscale the icon (e.g. 128x128) and keep a single copy, or reference the root file from CMake.
- [`ThighUSSegmentation/ThighUSSegmentation.py:239-245`](https://github.com/UPNa-Biomedical-Engineering-Group/SlicerThighUSSegmentation/blob/643350419b387f40c98699944d03c23e9cfd2b02/ThighUSSegmentation/ThighUSSegmentation.py#L239-L245): sanitizeCaseId (lines 150-166) replaces slashes and similar characters but does not reject '.' or '..'. The case ID is used as a path component at line 745 (caseDir = outputRoot / caseId), so '..' writes outputs (the input MHA, the CSV, and the segmentation) into the parent of the chosen output folder. The inputMhaPath.unlink() at lines 750-751 also targets a file in that location. The impact is limited to user-typed input, but it does write outside the selected folder. Reject case IDs equal to '.' or '..' (or that start with '.') in sanitizeCaseId, and verify after joining that caseDir resolves inside outputRoot.
- [`ThighUSSegmentation/ThighUSSegmentation.py:352-355`](https://github.com/UPNa-Biomedical-Engineering-Group/SlicerThighUSSegmentation/blob/643350419b387f40c98699944d03c23e9cfd2b02/ThighUSSegmentation/ThighUSSegmentation.py#L352-L355): The repository contains only the GUI; all image processing, inference and the Zenodo download/extraction happen in whatever `thigh-us-segmentation` release is newest at install time (no upper bound, no hash). A future release of that package runs with full user privileges inside Slicer without any further review, and the model archive is loaded by nnU-Net (torch checkpoint loading) from a network download. Nothing malicious was found in the reviewed code, but the reviewed code is not what actually processes the images. Pin an exact reviewed version (or a narrow range) and document the reviewed package version and model archive checksum in the README.
- [`ThighUSSegmentation/ThighUSSegmentation.py:292-297`](https://github.com/UPNa-Biomedical-Engineering-Group/SlicerThighUSSegmentation/blob/643350419b387f40c98699944d03c23e9cfd2b02/ThighUSSegmentation/ThighUSSegmentation.py#L292-L297): distancesWereCalculated is only false when df_results is empty. The message always says the femur was not detected, which may not be the actual failure (for example, a failed nnU-Net run that returns no results). Users may draw the wrong conclusion from the warning.
- [`ThighUSSegmentation/ThighUSSegmentation.py:678-680`](https://github.com/UPNa-Biomedical-Engineering-Group/SlicerThighUSSegmentation/blob/643350419b387f40c98699944d03c23e9cfd2b02/ThighUSSegmentation/ThighUSSegmentation.py#L678-L680): The consent dialog correctly asks before downloading. The download and extraction occur inside the external library (not in this repo), and no checksum or signature check is visible in this module. A corrupted or tampered archive would be accepted silently. This could not be verified in the repo. Ask the library to verify a published SHA-256 for the Zenodo archive before extracting, and document the checksum in the README.
- [`ThighUSSegmentation/ThighUSSegmentation.py:661-669`](https://github.com/UPNa-Biomedical-Engineering-Group/SlicerThighUSSegmentation/blob/643350419b387f40c98699944d03c23e9cfd2b02/ThighUSSegmentation/ThighUSSegmentation.py#L661-L669): A model is only considered present if `fold_0`..`fold_4` checkpoints all exist. If the Zenodo archive ships a single fold (common for nnU-Net releases), the extension asks the user to authorise a multi-GB download on every Apply, and the library may re-download each time. I could not inspect the archive contents to confirm which folds it contains. Treat the model as present when the folds actually used by the pipeline exist (or when the library reports the model as available), and remember the user's authorisation.
- [`ThighUSSegmentation/ThighUSSegmentation.py:27`](https://github.com/UPNa-Biomedical-Engineering-Group/SlicerThighUSSegmentation/blob/643350419b387f40c98699944d03c23e9cfd2b02/ThighUSSegmentation/ThighUSSegmentation.py#L27): The repository has no `ThighUSSegmentationTest` class, no `Testing/` directory and no CI workflow (only 9 files total), so the extension's own logic (case-ID sanitising, markup ordering, dependency checks) is untested and regressions would only surface at runtime for users. Add a `ScriptedLoadableModuleTest` covering `sanitizeCaseId`, `sort_markups_loading_order` and the dependency checks, plus a minimal CI workflow.
