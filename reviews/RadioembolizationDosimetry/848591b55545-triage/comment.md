Suggestions for a later update:

- [`Taranis/TaranisLib/ai.py:436-437`](https://github.com/4burakfe/SlicerRadioembolizationDosimetry/blob/848591b55545bd62aa27c2001be71c59a76944e3/Taranis/TaranisLib/ai.py#L436-L437): The .pth files come from a GitHub release and are unpickled by torch.load. In ai.py the download is SHA256-pinned (ai.py:172-174), which mitigates tampering, but the same pattern appears in LSFcalc/LSFcalc.py:1710 whose download path I could not verify, and on PyTorch < 2.6 the default is weights_only=False, so a replaced release asset would execute code. A user-supplied models folder (SETTING_MODELS_FOLDER) is also searched, so arbitrary local .pth files are loaded. Pass weights_only=True to torch.load (state_dicts load fine) and verify the SHA256 in the LSFcalc download path as well.
- [`Taranis/TaranisLib/ai.py:27-28`](https://github.com/4burakfe/SlicerRadioembolizationDosimetry/blob/848591b55545bd62aa27c2001be71c59a76944e3/Taranis/TaranisLib/ai.py#L27-L28): The extension is MIT, but the SwinUNETR weights it downloads come from a different repository (SlicerAether) and no licence or terms for those weights are given in the code or (as far as I read) the README. Users and redistributors cannot tell whether the weights may be used clinically or commercially. State the licence/provenance of the model weights (training data, terms) in the README and next to the download.
- [`LSFcalc/LSFcalc.py:1710`](https://github.com/4burakfe/SlicerRadioembolizationDosimetry/blob/848591b55545bd62aa27c2001be71c59a76944e3/LSFcalc/LSFcalc.py#L1710): LSFcalc loads the same weights the same way, so the same risk applies to the LSF module's model folders. Use weights_only=True and share the verified loader between the two modules.
- [`Taranis/CMakeLists.txt:50-54`](https://github.com/4burakfe/SlicerRadioembolizationDosimetry/blob/848591b55545bd62aa27c2001be71c59a76944e3/Taranis/CMakeLists.txt#L50-L54): Taranis/Testing/Python contains 9 test files (e.g. test_rules.py) but Taranis/CMakeLists.txt never does add_subdirectory(Testing), so those tests are neither built nor run by the extension's CI, unlike the other modules which have a Testing/CMakeLists.txt. Add add_subdirectory(Testing) under BUILD_TESTING and register the test files, or remove the unused directory.
- [`LSFcalc/Testing/Python/CMakeLists.txt:2`](https://github.com/4burakfe/SlicerRadioembolizationDosimetry/blob/848591b55545bd62aa27c2001be71c59a76944e3/LSFcalc/Testing/Python/CMakeLists.txt#L2): The per-module Testing/Python CMakeLists for LSFcalc, easy_reg, and the dosimetry modules only contain commented-out slicer_add_python_unittest calls. Only the hub has unit tests wired into the build, so regressions in those modules would not be caught by CI. Register the existing module tests, or remove the empty test directories.
- [`Taranis/TaranisLib/case.py:224`](https://github.com/4burakfe/SlicerRadioembolizationDosimetry/blob/848591b55545bd62aa27c2001be71c59a76944e3/Taranis/TaranisLib/case.py#L224): The cache is keyed by node ID and instance UIDs and is never cleared, so loading many series in a long session keeps growing it (and keeps stale entries for deleted nodes). Small leak, but it also means a volume whose DICOM header changed is never re-read. Clear the cache on scene close or cap its size.
- [`CBCTPlanning/CBCTPlanning.py:31`](https://github.com/4burakfe/SlicerRadioembolizationDosimetry/blob/848591b55545bd62aa27c2001be71c59a76944e3/CBCTPlanning/CBCTPlanning.py#L31): When TaranisLib cannot be imported, these modules append a Taranis folder to sys.path. This is a global side effect at import in Slicer's process and may pick up an unrelated TaranisLib package. It is only reached in the fallback branch. Rely on the extension's CMake install, which already installs TaranisLib next to each module, or remove the fallback for release builds.
- [`CMakeLists.txt:11-12`](https://github.com/4burakfe/SlicerRadioembolizationDosimetry/blob/848591b55545bd62aa27c2001be71c59a76944e3/CMakeLists.txt#L11-L12): Four screenshots (~1.5 MB each), taranis_logo.png (620 KB) and four copies of banner.png (1.7 MB each) are committed, so every extension build and checkout downloads ~10 MB of images that are only used for documentation and the module panel. The automated scan also reported much larger PNG/JFIF files (7-11 MB) that I could not read. Downscale the screenshots and banners (a few hundred KB is enough) or host them outside the build tree.
