Suggestions for a later update:

- [`GastricConduit/GastricConduit.py:54-58`](https://github.com/dhnihaoya/SlicerGastricConduit/blob/9f024f654368bc1b2dad2722adaf0c5d9bf8ad3e/GastricConduit/GastricConduit.py#L54-L58): GastricConduit/CMakeLists.txt:39-41 registers this file with slicer_add_python_unittest, so the extension's automated test reports success while asserting nothing; the real pytest suite is never exercised by the Slicer build. Separately, GastricConduit/Testing/__init__.py exists in the repository but is absent from MODULE_PYTHON_SCRIPTS (CMakeLists.txt:17-25), so the installed Testing directory is not a package. Add at least one real assertion to runTest (e.g. import GastricConduitLib and check volume_cm3), and add Testing/__init__.py to MODULE_PYTHON_SCRIPTS.
- [`GastricConduit/GastricConduitLib/download.py:63-66`](https://github.com/dhnihaoya/SlicerGastricConduit/blob/9f024f654368bc1b2dad2722adaf0c5d9bf8ad3e/GastricConduit/GastricConduitLib/download.py#L63-L66): The URL actually used is whatever asset happens to be first on the repository's latest GitHub release (widget.py:368), not the pinned DEFAULT_RELEASE_ASSET, and the downloaded zip is extracted and later loaded by nnU-Net as checkpoint_final.pth (a torch.load/pickle deserialization). There is no hash or signature check, so a renamed or replaced release asset would be deserialized as code. The risk is bounded by HTTPS from the author's own repository and the user's confirmation dialog, but the pinning intent expressed in version.py ('Weight zip stays on the v0.1.0 GitHub Release') is not enforced. Download the pinned release asset by name and verify a published SHA-256 before extraction; treat the 'latest release' lookup as an optional update check only.
- [`GastricConduit/GastricConduitLib/widget.py:245`](https://github.com/dhnihaoya/SlicerGastricConduit/blob/9f024f654368bc1b2dad2722adaf0c5d9bf8ad3e/GastricConduit/GastricConduitLib/widget.py#L245): _log is connected to logic.progressInfo (widget.py:573) and to InstallLogic.progressInfo. If PythonQt delivers those signals with a direct connection from the inference worker thread, processEvents() runs off the GUI thread, which is not supported by Qt and can crash Slicer; even on the GUI thread it re-enters the event loop during inference callbacks. Use a queued connection (or a Qt signal on the widget) and drop processEvents() from the log path.
- [`GastricConduit/GastricConduitLib/widget.py:337-339`](https://github.com/dhnihaoya/SlicerGastricConduit/blob/9f024f654368bc1b2dad2722adaf0c5d9bf8ad3e/GastricConduit/GastricConduitLib/widget.py#L337-L339): When setupPythonRequirements() returns False the panel simply returns to idle; no errorDisplay is shown, so the user sees the Apply button reappear with no explanation of why nothing ran (the reason, if any, only reaches the log widget). Report the failure with slicer.util.errorDisplay and point to the NNUNet extension's installer.
- [`GastricConduit/GastricConduitLib/widget.py:558-562`](https://github.com/dhnihaoya/SlicerGastricConduit/blob/9f024f654368bc1b2dad2722adaf0c5d9bf8ad3e/GastricConduit/GastricConduitLib/widget.py#L558-L562): Every Apply calls the NNUNet extension's setupPythonRequirements(), which can install nnunetv2 and PyTorch into Slicer's shared Python. Delegating to the NNUNet extension is the sanctioned path (no pip_install or torch pin here), but the user is never told that pressing Apply may install packages or download hundreds of MB; the panel only shows 'Checking Python dependencies…'. Show a confirmYesNoDisplay before the first dependency install, stating what will be installed and roughly how large it is.
- [`GastricConduit/GastricConduitLib/widget.py:366-368`](https://github.com/dhnihaoya/SlicerGastricConduit/blob/9f024f654368bc1b2dad2722adaf0c5d9bf8ad3e/GastricConduit/GastricConduitLib/widget.py#L366-L368): latest_release_asset_url() performs a blocking HTTPS request with a 10 s timeout (download.py:51-62) inside the Apply handler, before any dialog. On a slow or firewalled hospital network the panel freezes for up to 10 s with no feedback, and the request to api.github.com happens even for users who already have valid weights. Skip the release lookup when weights already validate, and run it off the GUI thread or with a shorter timeout plus a status message.
- [`README.md:19`](https://github.com/dhnihaoya/SlicerGastricConduit/blob/9f024f654368bc1b2dad2722adaf0c5d9bf8ad3e/README.md#L19): The research-use disclaimer is present, which is good, but nothing in the README states how the Dataset003 fold-5 model was trained or validated (case count, Dice/HD, external test set), and there is no sample data or tutorial beyond the screenshot. Users cannot judge whether the conduit volume is trustworthy for their population. Add a short validation section (dataset size, fold-5 metrics, any external test) and a small sample CT or link to public data.
- [`GastricConduit/GastricConduitLib/download.py:44-48`](https://github.com/dhnihaoya/SlicerGastricConduit/blob/9f024f654368bc1b2dad2722adaf0c5d9bf8ad3e/GastricConduit/GastricConduitLib/download.py#L44-L48): Users who follow the documented offline path (README.md:34, extract the zip manually) have no download_info.json, so are_weights_outdated() is always True and widget.py:373-375 shows 'A newer model is available. Download it now?' on every Apply. Declining works, but the prompt is misleading and repeated. Treat a valid model tree without download_info.json as up to date, or record the URL when the tree validates.
